---
title: "Local Web Viewer"
description: "Browse a run in a local dashboard with natsuhat view"
---

Every scan writes its results to disk as it runs. `natsuhat view` serves those files in a local dashboard, for a live run or a finished one.

```bash
natsuhat view                                    # the most recent run
natsuhat view my-run-name                        # a specific run under ./natsuhat_runs
natsuhat view --host 0.0.0.0 --port 8080 --no-open
```

The UI ships prebuilt with Natsuhat, so there is no extra install and no JavaScript build step. Reading saved runs does not upload them, and you do not need a hosted account. Launching scans uses your configured LLM provider. There is no remote report-email or feedback service.

For a multi-user hosted dashboard, `natsuhat view --hosted` explicitly enables
Supabase Auth, workspace roles, PostgreSQL, and private Storage. See the
[Supabase setup guide](https://github.com/nayakayp/strix/blob/main/docs/supabase.md)
for migrations, runtime credentials, email templates, and deployment. It uses
individual sign-in instead of the local viewer's shared link; it does not
automatically import or upload local runs.

## Options

<ParamField path="run" type="string">
  Run name under `./natsuhat_runs`. Defaults to the most recent run.
</ParamField>

<ParamField path="--host" type="string" default="127.0.0.1">
  Host to bind to. Use `0.0.0.0` to reach the viewer from other machines.
</ParamField>

<ParamField path="--port" type="number" default="0">
  Port to serve on. The default selects an available ephemeral port.
</ParamField>

<ParamField path="--no-open" type="boolean">
  Do not open the browser automatically.
</ParamField>

<ParamField path="--manage-scans" type="boolean">
  Enable starting and stopping local or remote scans from the authorized dashboard. Off by default.
</ParamField>

## What Is In The Dashboard

- **Overview** — a compact summary followed by findings and severity counts. Run configuration and the full report are collapsed until opened; there is no separate Issues tab.
- **Findings** — select a row to read its complete Markdown in a right-side panel, including evidence, reproduction steps, and remediation. The panel fills the screen at narrow widths. Close it with Escape or the close button without losing your place in Overview.
- **Agents** — an expandable parent–child tree with the selected agent's transcript alongside it. Live activity follows new events only when you are already reading at the bottom.
- **Steering** — send instructions to a live scan to redirect the agents during the run. Steering works only in the dashboard the running scan opens. A standalone `natsuhat view` has no live scan to steer.
- **History** — browse runs alongside the opened run in the same `natsuhat_runs/` directory. The private viewer link authorizes access; email verification is not required.
- **Scans** — start an isolated E2B scan, inspect its status and log, stop it, and open its results. Available only with `--manage-scans`.
- **Reports** — read the report saved locally with each run.

## Managing Scans

```bash
uv run --frozen natsuhat view --manage-scans --port 8080 --no-open
```

Open the private URL printed by the command, then choose **Scans**. This
works before the first run exists. Management currently requires Linux or macOS
and a Python installation (uv/pip), not the standalone bundled executable.

Configure `E2B_API_KEY`, access to the published stable E2B release, and your LLM provider.
The dashboard server does not need Docker; the E2B template contains Docker and
the tool image. Choose a target URL, domain, IP, GitHub repository, or ZIP upload,
not a server filesystem path. Only submit targets you may test.

Each start requires a target, scan mode, LLM budget in USD, and explicit
authorization. Set a positive amount for a spending cap, or **`-1` for unlimited
LLM spending**. Zero, other negative values, and non-finite values are rejected.
Unlimited jobs are shown as **Unlimited LLM budget**; their workers omit the
CLI's `--max-budget` flag, using the engine's existing uncapped behavior.
In-flight model calls can overshoot a finite budget. Up to
ten E2B scans may run concurrently by default. Additional starts for a full runner
pool return `409` rather than queueing. Independently launched CLI scans are not
managed or counted.

Failed, stopped, and interrupted jobs show **Resume scan** when their saved agent
checkpoint and session database are available. This continues the same run ID,
conversation history, findings, and source snapshot, using the currently selected
LLM settings. Confirm authorization again and set a **total** LLM budget: earlier
spending still counts. An exhausted cap must be increased, or set to `-1` for
unlimited spending. Existing concurrency limits still apply. There is no
fresh-start retry action; use **New scan** to start over. When a scan cannot
resume, its card shows the reason.

Resumes restore the original retained E2B sandbox and use its
installed engine, not the current stable image or a newly created VM. A small
dashboard resume adapter supports older retained images with CLI checkpoint
support; dependencies and security tools are not reinstalled. Resumed provider
compute is billable. Resuming does not
restore terminated commands, network connections, or in-flight model requests;
agents continue from their latest saved checkpoint. Completed scans, missing
checkpoints, and missing remote sandboxes cannot resume. Pending results or
unconfirmed cleanup must be recovered first.

If result transfer fails, **Retry results** retrieves files from the retained
sandbox without launching another scan. It briefly resumes provider compute,
then pauses the sandbox again; provider charges may apply. Recovery
is explicit, survives dashboard restarts, and blocks **Resume scan** until results and
retention are confirmed. A partial recovered run is marked interrupted rather
than left running. Findings withdrawn on the worker are removed from subsequent
dashboard snapshots; controller job metadata is preserved.

Jobs and their logs are persisted in `natsuhat_runs/<job-id>/job.json` and `job.log`,
alongside normal run artifacts. Logs may contain sensitive scan output and remain
on disk. Failed cards show the saved failure reason and a collapsed **Failure log**
with the last 32 KiB of each controller and remote log. **Retry loading log** retries
only the log read, not the scan. Running and successful cards have no log control.
Click a card to open scan details.
Website, repository, and ZIP scans have distinct icons. Hover or focus an action
icon to see its label; stopping, deleting, and recovery do not open the card.

Closing the browser does not stop the scan. Stopping the viewer stops its active
children with SIGTERM. Workers get up to eighteen minutes for final
synchronization and E2B pause before a stuck process is force-killed.
Completed job history survives viewer restarts. After an unexpected viewer exit,
an inherited owner lock prevents another manager from starting until its old
worker exits; stale active records are then marked interrupted. There is no
automatic restart, adoption of saved PIDs, or automatic scan resumption. Use
**Resume scan** explicitly after recovery if a checkpoint is available.

### E2B Sandbox

E2B is the only dashboard runner. Set `E2B_API_KEY` on the dashboard server using
a secret manager, not a committed file. A missing key blocks scans; there is no
local Docker fallback. **`nayakas-project/natsuhat-runner:stable` is the only
template source.** Saved template selections and `NATSUHAT_E2B_TEMPLATE` do not
override it. **Settings → Sandbox → E2B** displays this fixed source and offers
read-only availability checks.

The settings page displays failures only. Missing or unavailable stable releases,
or releases without a unique `rev-<content hash>` tag, are rejected before creating
a job or billable VM. Every new scan resolves stable afresh and saves its pinned
revision tag. Settings checks expire after 60 seconds; scan submission never uses
that cached selection. Existing jobs keep their original release even when stable
is promoted. The worker checks the actual manifest against the pinned release and
checks the prepared runtime and Docker image before sending LLM credentials.
Local application or dependency changes do not invalidate the published release.
An unrelated newer failed or building release does not invalidate a ready stable
build. Availability checks never build an image or start a sandbox.

To intentionally update the scan runtime, publish the authoritative family:

```bash
uv run --frozen python scripts/runner_images.py --release nayakas-project/natsuhat-runner
# Later updates can reuse the prepared stable image:
uv run --frozen python scripts/runner_images.py --release nayakas-project/natsuhat-runner --base nayakas-project/natsuhat-runner:stable
```

These commands create persistent, potentially billable E2B resources.
The builder creates `nayakas-project/natsuhat-runner:rev-<full content hash>` and, by default,
checks a fresh sandbox and the same sandbox after pause/resume before promoting
`nayakas-project/natsuhat-runner:stable`. Failed smoke tests leave stable unchanged. Existing
revision tags are reused and rechecked, never overwritten by this builder.
Older revision tags remain available for rollback: publish again from the desired
checkout to promote its release back to stable. E2B tags
can be reassigned externally, so the worker still verifies the actual manifest.
`--skip-smoke` explicitly bypasses sandbox tests and publishes after the build
finishes; it does not establish runtime compatibility. Stable controls the installed
scan engine; it is neither an automatic build nor a bypass for manifest checks.

The image source is `containers/runner/`. The builder
installs the exact application and frozen Python dependencies and builds the
Kali tool image **once**, before saving the template. This one-time
build may take tens of minutes. E2B captures Docker already running.

Every submitted remote scan gets a separate VM with its application, dependencies,
and tools already installed. The controller checks the pinned release and prepared
Docker image, sends only the job, optional instructions and LLM connection, and
launches the installed Python directly. There is **no per-scan source upload,
dependency installation, image pull, or tool build**. Missing, mismatched, or incomplete
images fail clearly before receiving model credentials; there is no cold-build fallback.
Local server source directories, Git history, other runs, and E2B credentials
are not uploaded. Remote targets must be reachable URLs, domains, IPs, or HTTPS
repositories, not local paths or credential-bearing URLs. A remote `localhost`
refers to that new VM, not the dashboard server.

The selected LLM connection, including its API key, is sent to the worker.
Results and consistent SQLite transcript snapshots are pulled about every five
seconds while scanning; no public callback or inbound worker port is required.
The dashboard must remain running. Final reports remain in the controller's
`natsuhat_runs/<job-id>/` as well as in the retained sandbox. Remote live steering
and restarting an interrupted scan after a controller restart are not supported.
Result snapshots are limited to 256 MiB.

The LLM budget does **not** include provider compute charges. The total remote
time limit defaults to 14,400 seconds (four hours), including provisioning and paused
time; change it with
`NATSUHAT_REMOTE_TIMEOUT_SECONDS` (300–86,400). Change the shared remote pool with
`NATSUHAT_REMOTE_MAX_CONCURRENT` (1–16, default 10).

E2B sessions run for at most 3,600 seconds before **pausing**, preserving memory,
processes, and files. While a scan is active, the controller reconnects to the
same VM and continues polling its existing process; it does not launch the scan
again or reset the LLM budget or overall deadline. Provider resume failures are
retried within the existing connection retry limit. Network connections may
need to reconnect after a pause; preserving memory is not a guarantee that an
in-flight model or tool request survives unchanged.
If E2B falls back to a filesystem-only snapshot under snapshot pressure, the
controller detects the reboot and fails the scan without replaying it. Its files
and existing results remain retained; process-memory recovery is not possible.

Completion, cancellation, and failures retain E2B sandboxes **paused** without
deleting their data.
Traffic-triggered E2B auto-resume is disabled, so an old URL cannot restart compute.
Paused E2B resources are not automatically resumed when the dashboard restarts.
If the controller disappears, E2B pauses at its session timeout.
Retained sandboxes and credentials in their memory
remain subject to your provider account's access controls and retention policies.
Check current provider pricing for paused storage and retained images.
Unconfirmed pause
shows **Retry cleanup** and blocks resuming that job. After a controller
restart, unresolved E2B resources are paused without restarting scans.
Verify the provider console if cleanup remains unconfirmed. Historical scans
from other runners remain readable, but cannot be resumed or recovered through
this dashboard. Recover their remote resources with the original provider.

The session-protected JSON endpoints are:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/jobs` | List jobs, resume eligibility/reason, runner availability/default, concurrency limits, remote phase/cleanup/resume count, and result availability |
| POST | `/api/jobs` | Start with `target`, `scan_mode`, `max_budget_usd`, `authorized: true`, optional `runner` (`e2b` only, also the default), and optional `instruction` |
| POST | `/api/jobs/<id>/resume` | Continue a failed/stopped/interrupted checkpoint with `authorized: true` and optional `max_budget_usd` (total cap, defaults to the previous cap); unavailable checkpoints or capacity return `409` |
| POST | `/api/jobs/<id>/stop` | Stop a job, recover pending results, or retry failed remote cleanup (safe to repeat; result recovery can resume compute) |
| GET | `/api/jobs/<id>/log` | Read the log tail |

Mutations require `Content-Type: application/json` and the viewer session cookie;
cross-origin browser requests are rejected. This is a trusted, single-operator
local service, not a multi-tenant public API. Keep it behind a firewall or an
authenticated private proxy. Anyone with its authorized link can launch scans
using the server's credentials and access server-local targets.

### LLM Settings

With `--manage-scans`, open **LLM settings** in the dashboard's top bar. Add
connections for OpenAI, OpenRouter, Anthropic, Ollama, or an OpenAI-compatible
endpoint. **Save & fetch models** saves the connection and lists its available
models without generating tokens. Choose a fetched model or enter its provider
model ID manually; model availability does not guarantee tool-calling support.
Use the API root for Anthropic/Ollama and the versioned API base (usually `/v1`)
for OpenAI-compatible endpoints. Addresses are reached from the viewer server.

Set prices in **USD per million tokens**. Leave all prices blank for the engine's
automatic accounting, or supply both input and output prices; zero means free.
An omitted cached-input override uses the input price. Overrides are retained
per model. OpenRouter's returned token prices can be copied into these fields
with **Use fetched prices**. Prices affect estimates and LLM budget enforcement,
not the provider's actual bill. For unrecognized custom models, supply manual
prices to make budget estimates meaningful.

**Save & use for new scans** selects the default connection/model for subsequent
dashboard jobs. An already running job keeps its original connection and prices.
**Use server CLI settings instead** restores the previous CLI/environment behavior;
dashboard settings never overwrite the global CLI configuration.

Profiles survive restarts in `~/.natsuhat/dashboard/<workspace-hash>/llm-providers.json`.
The hash identifies the workspace's canonical absolute path. The dashboard
automatically migrates the old workspace `.natsuhat/llm-providers.json`, verifies the
saved data, then removes the old copy. Conflicting copies stop startup without
overwriting either one. Keys remain **unencrypted**, with directory mode `0700`
and file mode `0600`, and are never returned by the API. The credential directory
is hidden behind an empty read-only mount for local scans and excluded from
source uploads, even when scanning a parent/home directory or opting into hidden
and sensitive files. It cannot itself be a scan target. Keep it out of backups
you share. A blank API-key replacement retains the existing
key; use the removal checkbox to clear it. Changing a connection's endpoint
requires re-entering or explicitly removing its key. Model discovery does not
follow redirects, to avoid forwarding credentials to another host.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/llm/settings` | Profiles and selected default, without keys |
| POST | `/api/llm/providers` | Create/update a connection, model, and per-model prices |
| POST | `/api/llm/models` | Fetch models for a saved provider `id` |
| POST | `/api/llm/select` | Select a provider `id`, or `null` for CLI settings |
| POST | `/api/llm/delete` | Remove a saved provider `id` |

These endpoints use the same session, management opt-in, JSON-only, and
cross-origin protections as scan jobs. Only configure endpoints you trust;
the selected endpoint receives its saved API key.

### Server Sizing

For one scan using a hosted LLM, a reasonable starting estimate is **4 vCPUs,
8 GB RAM, and 40–60 GB SSD**. For heavier browser/build workloads, start with
**8 vCPUs and 16 GB RAM**. These are planning estimates, not benchmarked minimums;
monitor actual memory, CPU, image size, and artifact growth. No GPU is needed
unless you host the model yourself.

Docker resource limits are opt-in: set `NATSUHAT_SANDBOX_MEM_LIMIT`,
`NATSUHAT_SANDBOX_CPUS`, `NATSUHAT_SANDBOX_SHM_SIZE`, and optionally
`NATSUHAT_SANDBOX_PIDS_LIMIT` in the server environment. Leave capacity for the host
and viewer outside the sandbox limits. The job budget limits estimated LLM
spending, not server CPU, memory, or wall-clock time.

## Sharing The Link

<Warning>
  The token in the printed URL grants access to run data and live steering. With `--manage-scans`, it also grants scan execution using the server's provider credentials. Share it only with trusted users.
</Warning>

To reach the viewer from another machine, start it with `--host 0.0.0.0` and replace `0.0.0.0` in the printed URL with a reachable IP address or hostname. Restrict the port with your firewall. A request without the token-derived session cannot read run data.
